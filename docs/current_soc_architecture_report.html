Cheshire CVA6 + Ara + FFT / VCU118 SoC 架构与地址空间分析

分析对象：/home/user06/work/xinkailai/cheshire，分支 ara-vcu118，当前工作区包含未提交的 FFT/VCU118 相关改动。

生成日期：2026-10-03。本文只基于当前源码与已生成脚本做静态分析；没有修改 RTL、C 源码或构建脚本。

1. 结论摘要

SoC 主体

顶层 SoC 是 hw/cheshire_soc.sv。它以 CVA6 为核心，通过一个主 AXI crossbar 连接调试模块、LLC/SPM、DMA、Ara、FFT、VGA/USB 等 AXI master 或 slave，再通过 AXI-to-Regbus 适配器访问低速外设。

VCU118 封装

板级顶层是 target/xilinx/src/cheshire_top_xilinx.sv。VCU118 打开 DDR4、JTAG、QSPI/STARTUPE3、VIO 和 reset；DDR4 通过 dram_wrapper_xilinx.sv 接到 SoC 的 LLC 外部 AXI master 端口。

地址分配

地址空间由 hw/cheshire_pkg.sv 中的 gen_axi_out() 和 gen_reg_out() 生成；实际译码在 hw/cheshire_soc.sv 的 axi_xbar 与 addr_decode + reg_demux 中完成。

FFT 集成方式

FFT 不是 MMIO 外设，没有单独寄存器窗口。它复用 CVA6 的 accelerator/CVXIF 类接口，与 Ara 通过 multi_accel_router 按指令 opcode 分流，并作为独立 AXI master 访问现有内存地址。

当前构建脚本状态：target/xilinx/scripts/add_sources.vcu118.tcl 当前定义了 ARA、NR_LANES=2、VLEN=2048，但没有定义 FFT_ACCEL。源码已经有 Cfg.Fft、FFT RTL 和路由逻辑；若要在 VCU118 bitstream 中实际实例化 FFT，需要确保构建时带上 FFT_ACCEL 宏并重新生成/使用对应 Vivado source script。

2. 当前 VCU118 配置来源

配置链路如下：

  1. hw/cheshire_pkg.sv 定义 cheshire_cfg_t、DefaultCfg、地址常量和地址映射函数。
  2. target/xilinx/src/cheshire_top_xilinx.sv 的 gen_cheshire_xilinx_cfg() 从 DefaultCfg 复制配置，并针对 FPGA 覆盖少量参数。
  3. target/xilinx/src/phy_definitions.svh 根据 TARGET_VCU118 打开板级 IO 宏。
  4. cheshire_soc #(.Cfg(FPGACfg)) 接收最终配置，内部生成 AXI/Regbus 端口数量和地址规则。

这表示板级已接出 reset、JTAG、DDR4、QSPI flash 访问路径和 VIO。I2C、SD、VGA、USB、fan 等宏没有在 VCU118 分支中打开。注意：这不等同于 SoC 内部外设配置全部关闭；例如 DefaultCfg 仍默认开启 I2C、GPIO、VGA，除非 FPGA 配置函数覆盖。

3. SoC 结构

3.1 高层数据通路

CVA6 core
  |-- AXI master ---------------------------------------------.
  |                                                           |
  |-- accelerator request --> multi_accel_router --> Ara ---- | --> AXI master
                         |                     \              |
                         `--------------------> FFT accel ----'

Debug SBA / DMA / VGA / USB / external AXI masters --------------> AXI xbar

AXI xbar outputs:
  [0] Debug Module AXI slave
  [1] AXI-to-Regbus adapter -> Reg demux -> CLINT/PLIC/UART/SPI/GPIO/...
  [2] LLC/SPM/DRAM path
  [3] DMA config AXI slave
  [external] optional AXI subordinate ports

LLC master output -> Xilinx DDR4 wrapper -> VCU118 DDR4 MIG

模块/文件职责与地址空间关系
hw/cheshire_pkg.sv配置结构、默认配置、静态地址常量、AXI/Regbus 端口和规则生成函数。地址分配的单一核心来源。
hw/cheshire_soc.svSoC 顶层，实例化 AXI crossbar、Regbus demux、CVA6、Ara、FFT、调试模块、外设。把 AxiMap 接到 axi_xbar，把 RegMap 接到 addr_decode。

4. 地址空间如何分配

4.1 分配机制

Cheshire 的地址分配不是散落在外设实例化处手写的，而是由配置结构生成：

层级函数/模块输入输出
AXI crossbar 输入端口gen_axi_in(Cfg)哪些 AXI manager 启用：core、debug、Ara、FFT、DMA、VGA、USB、external mastersAxiIn.* 端口编号
AXI crossbar 输出端口和规则gen_axi_out(Cfg)LLC/SPM/DRAM/DMA/SerialLink/external rulesAxiOut.* 端口编号与 AxiMap
Regbus demux 输出端口和规则gen_reg_out(Cfg)Boot ROM、CLINT、PLIC、UART、I2C、SPI、GPIO、VGA、BusErr 等开关RegOut.* 端口编号与 RegMap
实际译码axi_xbar, addr_decode, reg_demuxAxiMap, RegMap把访问请求送到具体 slave；Regbus 未命中进 error slave。
地址规则是半开区间：源码中用 start 和 pte/end_addr 表示 [start, end)。例如 0x0300_2000..0x0300_3000 是 4 KiB UART 窗口。

6. Ara 与 FFT 共享接口分析

6.1 CVA6 accelerator 接口路径

CVA6 输出 cvxif_req_o，输入 cvxif_resp_i。原始 Ara 集成通常直接把这组信号接到 Ara；当前分支加入了 multi_accel_router：

CVA6 cvxif_req_o
  -> acc_req
  -> multi_accel_router
      if FFT namespace: acc_req_fft -> fft_accelerator_ip
      else:             acc_req_ara -> ara
  <- acc_resp from selected unit
  -> acc_resp_pack -> CVA6 cvxif_resp_i

6.2 指令分流规则

hw/fft/src/fft_accel_pkg.sv 定义了 FFT 指令命名空间：

类别规则用途
FFT startopcode = 0x0b, funct3 = 0x5, insn[30:25] = 12, rd = x0从 rs1 取源地址，从 rs2 取目标地址，启动 4096 点 FFT/IFFT。
FFT/IFFT 选择insn[31]作为 inverse 位传给 FFT core。
FFT wait0x0000_002b等待当前 FFT epoch 完成，返回异常状态。
Ara不属于 FFT namespace 的 accelerator 请求转发给 Ara。

6.3 FFT 数据搬运

fft_accelerator_ip 内部包含命令队列、fft_task_ctrl、axi_from_mem 和 fftifftmain：

  • rs1 是输入 buffer 地址，rs2 是输出 buffer 地址。
  • fft_task_ctrl 固定处理 Points = 4096。
  • 当前 DataWidth = 64，每拍从内存读 4 个 16-bit 样本。
  • 输入样本打包为 {real16, 16'h0} 送入 FFT core。
  • 输出把 23-bit real/imag 符号扩展后打成 64-bit 写回内存。
  • AXI 请求经 axi_from_mem 发到主 AXI crossbar，因此可访问 SPM uncached alias、DRAM 等已有 AXI 地址。

6.4 软件调用方式

sw/tests/fft_accel_smoke.spm.c 和 fft_accel_dump.spm.c 使用内联汇编发自定义指令。测试中使用 SPM_UNCACHED_ALIAS = 0x04000000 把 0x1000_0000 附近的 SPM cached 地址转换到 0x1400_0000 uncached alias，减少缓存一致性干扰。

fft_exec(src, dst):  .insn r 0x0b, 0x5, 0x0c, x0, rs1, rs2
ifft_exec(src, dst): .insn r 0x0b, 0x5, 0x4c, x0, rs1, rs2
fft_wait():          .word 0x0000002b

8. 注意事项与风险点

项目说明建议
FFT 宏未进入已生成脚本 add_sources.vcu118.tcl 未包含 FFT_ACCEL，所以当前已生成 Vivado 工程脚本可能只启用 Ara。 重新生成 Bender Vivado script 或在构建流中显式加入 FFT_ACCEL，再确认 FPGACfg.Fft = 1。
FFT 无 MMIO 可见性 SoC registers 的 hw_features 当前没有 fft bit；软件无法通过该寄存器确认 FFT 是否存在。 如果需要运行时探测，可考虑扩展 cheshire_regs.hjson，但这属于后续源码修改。
VCU118 板级 IO 与 SoC 内部配置不完全一致 I2C/GPIO/VGA 可能在 SoC 内部仍实例化并有地址窗口，但 VCU118 顶层没有完整板级 IO。 区分“MMIO 可访问”和“外设信号接到板上”。文档、bring-up 和测试脚本中应按板级可用性选择外设。
Ara/FFT 共享 accelerator 接口的互斥 multi_accel_router 使用 pending owner 保证同一请求等待对应响应；FFT namespace 外的请求转给 Ara。 混合运行 RVV 和 FFT 时，应继续覆盖背靠背请求、异常、wait、fence/cache 场景。
FFT 与缓存一致性 FFT AXI master 直接读写内存；测试使用 SPM uncached alias 和 fence。 软件侧继续优先使用 uncached alias 或明确 cache maintenance/一致性策略。
